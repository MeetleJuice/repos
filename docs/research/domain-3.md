# Domain 3 — Structured agentic program repair

Research and read-only code audit, 19 October 2026. Recommendation: separate **evidence/diagnosis → constrained patch → deterministic independent validation** inside Foundry's existing bounded controller. This is a control-flow separation, not an unbounded group of autonomous agents.

## Evidence and source limits

- **RepairAgent**, authors' repository: https://github.com/sola-st/RepairAgent ; directly retrieved https://raw.githubusercontent.com/sola-st/RepairAgent/main/README.md . Its three states explicitly distinguish understanding a failing test, collecting relevant code, and trying/validating fixes. The repository reports **164 correctly repaired Defects4J bugs** and links the ICSE 2025 paper https://arxiv.org/abs/2403.17134 . This is an author-reported Java benchmark result, not a reproduced measurement and not an expected Foundry success rate. The repository explicitly distinguishes plausible (tests-pass) patches from correct patches.
- **RepairLLaMA**, authors' implementation: https://raw.githubusercontent.com/ASSERT-KTH/repairllama/main/README.md ; paper https://arxiv.org/abs/2312.15698 . Documents deliberate input/output representations and restricted single-function repair datasets. Supports measuring repair representation and context selection rather than assuming whole-file rewrites are best. Its fine-tuned Java models are not drop-in evidence for Ollama Python/JavaScript performance.
- **SWE-agent**, authors' repository: https://raw.githubusercontent.com/princeton-nlp/SWE-agent/main/README.md ; paper https://arxiv.org/abs/2405.15793 . Shows configurable execution/tool interfaces and reports current development shifting toward the simpler mini-SWE-agent. Supports bounded, inspectable interfaces; benchmark percentages in its README are not reproduced here or transferable guarantees.
- **InspectCoder and iCat-agent:** no authoritative matching primary source was successfully retrieved in this pass. Any supplied benchmark percentage, ranking, or claimed superiority for those names remains **unverified**; none informs a release performance claim. arXiv and GitHub API search returned proxy HTTP 403; raw GitHub author repositories above were accessible. This prevents an exhaustive latest-literature comparison.

## What the current implementation actually does

`forge/core.py::generate_and_apply` uses one coder request and at most one malformed-response correction, forcing complete changed files on correction. `apply` validates exact edits, portable paths, Python AST syntax, placeholders, owned documents, frozen-test hashes and 36,000-character source budget **before** checkpointed source replacement. These are meaningful safeguards, not merely prompt instructions.

`_inspect_and_repair`, `_verify_milestone`, and the runtime repair loop share a bounded remaining-repair allowance. Unchanged-source fingerprints stop repeated execution; environment failures bypass application repair. `forge/context.py::failure_feedback` supplies phase, diagnostic text, traceback tail, referenced files, and bounded browser action evidence. `forge/harness.py::diagnose` is deterministic category/string matching, not an independently validated root-cause analysis. Its isolated phases check approved HTTP behavior, real imported-app tests, launch, and persistence; manual/browser evidence remains necessary for gameplay. `tests/test_repairs.py`, `tests/test_workspace_cleanup.py`, and `tests/browser_repair_check.py` preserve frozen tests, failure evidence and historical shield regressions.

## Gaps and a bounded next step

**Contract gap:** failure feedback is helpful but the patch response does not carry a validated hypothesis, cited evidence, intended files and reproduction criterion. Add a bounded repair brief referencing existing failing evidence/check IDs; treat the hypothesis as a hypothesis. Derive file candidates from traceback/AST symbols and declared contracts, with a bounded fallback when localization is uncertain. Reject paths outside the source map; do not reject a necessary cross-file repair merely because it touches multiple files.

**Capability gap:** valid Python plus passing generated tests cannot prove a repair's intended behavior. Keep approved checks/frozen tests independent from patch authority. Candidate-created tests are supplementary evidence, not trusted replacement tests. Validate candidates in staging with syntax/contract checks, the targeted failing check, and applicable existing regressions before promoting them when execution was approved. Without execution consent, clearly retain 'candidate/files ready, not verified' status. Preserve source fingerprints and original evidence on rejection.

A separate LLM diagnosis call should be optional or reserved for repeated/ambiguous failures: it costs latency, quota and tokens and is not intrinsically more correct. Start with deterministic structured evidence and one constrained patch call; never let an LLM validator override test failures. Record diagnosis category, changed-file count, target-check result, regressions, tokens, latency and repair attempts. Evaluate on the actual Notes, dashboard malformed-response, shield-collision and cleanup-environment fixtures before claiming improvement. No throughput or success-rate gain has been measured by this research-only pass.
