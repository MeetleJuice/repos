# Local serving and harness evidence for Foundry v0.26

Scope: read-only repository research, public primary sources and proposed bounded experiments. No local inference, Windows hardware inspection, paid call, secret access, repository edit or routing change was performed. Research artifacts reside outside the checkout. Repository HEAD observed: `e4df92bfa3c5585a182ce5e5952a66d85e3560e2`. Source hashes in `static-measurements.json` bind the inspected files; `sources.json` records fetched URLs, retrieval UTC, bytes and SHA256. Raw sources are retained under `raw/`. Documentation on moving main/master branches is a dated snapshot, not evidence of the user's installed versions.

## What the reported failures establish

The supplied user observation is qwen2.5:7b reaching a roughly 120-second transport failure followed by deepseek-r1:7b producing `schema_error`. This establishes two different failure classes. It does not establish CPU-only inference, insufficient VRAM, a broken Ollama installation, a universally unsuitable model, or a successful generation benchmark. The exact prompt, runtime version, model digest, quantization, timings, loaded context and rejected proposal are unavailable in this lane.

`routing.py:42–45` defaults and caps selectable request timeouts at 120 seconds. `http_io.py:17–30` and `streaming.py:57–69` check elapsed time between socket reads; each blocked read can consume its socket timeout. Thus the configured 120 seconds is not a reliable whole-job hard deadline. A transport timeout may include model loading, queueing, prompt evaluation, reasoning, decoding and response delivery. A schema error means the proposal was rejected by the application's shape or consistency checks; it is not equivalent to invalid JSON or an unreachable runtime. `core.py:342–356` records this distinction.

## Confirmed repository issues and limits

1. **Conflicting planner examples.** `prompts.py:78–100` supplies two abbreviated full-proposal examples. Both omit schema-required `task_contract_version` and `context_policy`; every example task omits `outcome`, `files`, `depends_on` and `done_when`. Both show a single task despite prose asking for 2–16 and normally 4–10 focused tasks. The browser example bundles multiple interactions into one task. `prompt-example-audit.json` records the static comparison. This is direct evidence of conflicting guidance, not proof that it caused the supplied DeepSeek rejection. Keep historical legacy proposal handling intact: `tasks.py:15` deliberately accepts unversioned historical proposals.

2. **Large universal instruction packet.** PLAN is 10,440 characters / 10,450 UTF-8 bytes / 103 lines before the user request, starter plan, prior proposal, correction findings, output-contract suffix and framing. CODE is 5,416 characters / 5,420 bytes. These are byte/character measurements, not model tokens. `core.py:1100–1115` includes the prior proposal and, for arcade, a starter example in the request. A correction adds another full candidate and review findings in `planning.py`. The prompt mixes server CRUD, arcade edge cases, optional Chromium actions, persistence and output examples for every planner invocation. This supports a compact, complete, role-specific candidate experiment, not unilateral omission of requirements/source.

3. **JSON validity does not imply proposal validity.** Native Ollama gets `PLAN_SCHEMA` through `format` (`models.py:171–180`). It contains required names and some local bounds, but does not enforce cross-reference coverage, earlier-only dependencies, controller file ownership, meaningful HTTP assertions, nonempty behavior evidence, bounded task instructions or all array minimums. Deterministic `contracts.py`, `tasks.py`, evidence validation and approval remain essential. Do not weaken them to raise a success rate.

4. **Different local endpoints receive different constraints.** OpenAI-compatible `local` receives only `response_format: {type: json_object}` (`models.py:206–208`), not the role schema; native Ollama receives the schema. Therefore moving the same model to LM Studio/llama.cpp/vLLM can change constraint enforcement even with nominally similar endpoints. Add a tested, versioned runtime capability profile before introducing runtime-specific `json_schema`/grammar fields; never assume one OpenAI-compatible implementation accepts another's exact nesting or all JSON Schema keywords.

5. **Local thinking is not explicitly controlled or separately budgeted.** `capabilities.py:47–53` sets local supports_thinking_budget false and budget zero. `models.py` sends no Ollama `think`, local `reasoning_effort` or runtime-specific reasoning budget. This is an adapter declaration, not evidence that a reasoning model uses no reasoning tokens. The streaming parser displays only `message.content` / `delta.content`, so a runtime's separate thinking channel can be active without visible text progress. Do not log raw thinking by default or infer a hang from an empty content preview.

6. **A model-specific prompt mismatch is plausible.** The official DeepSeek-R1 README recommends no system prompt and temperature 0.5–0.7, while Foundry universally sends its long system prompt and temperature 0.2. This is primary-source justification for a fixture-only adapter experiment, not a universal rule for JSON generation and not evidence that temperature 0.6 will fix planning. Exact Ollama packaging/template/version still matters. Keep Qwen instruction and DeepSeek reasoning families separate in evaluation.

7. **Budget reservation is not GPU capacity.** Local context 32,768 and the unchanged planner floor 8,192 leave at most 24,576 estimated input tokens at that floor. The native schema is 3,574 JSON characters; the current conservative empty-user-input estimate is already 7,524 from PLAN plus schema and safety margin. Real user/starter/history payloads increase it. `capabilities.reserve` deliberately uses UTF-8 bytes/2 plus framing as a conservative heuristic, not actual tokenizer counts. It may reserve above the floor for structured tasks; the compact retry preserves the floor and all contract fields. `CapabilityRegistry.get` uses the selected context for a local planner output ceiling, not a discovered guarantee about a model/server. The OpenAI-compatible adapter does not configure the external server's context at all. A requested 32,768 context can increase KV-cache demand even for a smaller model. No exact VRAM requirement or fit claim follows from these values.

8. **Useful existing observability has gaps.** Ollama load, prompt-evaluation, generation seconds and generation tokens/second are already retained on completed responses (`models.py:187–191`). Missing: total runtime duration, prompt-cache count, client first byte/frame/content timing, separate queue/connection phases, and local-compatible timing extras. A timeout before the final metrics frame leaves backend durations unknown. A missing usage field must stay unknown. Do not turn `input_characters` into token counts or interpret catalog discovery as inference success.

9. **Streaming is operational feedback with cooperative cancellation.** Current transport caps wire bytes at 2 MB, refuses local redirects/proxies, discards incomplete/cancelled content, and closes responses from its worker. Its cancellation event is checked between reads; it cannot preempt a blocked socket read. A terminal finish reason or Ollama done frame is required; an SSE stream ending with no accepted completion remains an error. Client response closure does not by itself prove the external runtime cancelled GPU work. Verify server abort behavior before promising it. Partial previews must never become accepted source or verification evidence.

These serving stacks run model inference. Agent harness capabilities such as filesystem tools, checkpointing, execution isolation, requirement reconciliation, approval, bounded repair and evidence attribution are separate responsibilities. Tool-call-shaped model output does not execute a tool or authorize an action. Installing a server cannot grant a local model the Codex application's harness.

## Proposed bounded experiments (not executed)

Run only through an explicit local-only fixed-fixture action, serialized with inference, with diagnostics outside projects. Do not autodiscover cloud endpoints, reroute projects, execute generated code, promote source, change approved plans or alter the 8,192 planner floor. Current two-case 4,096-context calibration is response/edits diagnostics only; its success cannot certify 32,768-context planning.

**Phase A: inventory, no generation.** Record Windows/Ollama version, driver, exact GPU name, dedicated VRAM total/free, RAM, model tag+digest+quantization+template, requested context, loaded context when actually exposed, and CPU/GPU offload evidence. Use `ollama --version`, `ollama list`, `ollama ps`, local `/api/show` and `/api/ps`; inspect returned supported fields rather than assuming every version exposes all of them. In Windows Task Manager record dedicated and shared GPU memory separately and identify the compute/CUDA engine, rather than reading the default 3D graph. As an optional diagnostic on supported NVIDIA driver installations, capture `nvidia-smi --query-gpu=name,driver_version,memory.total,memory.used,utilization.gpu --format=csv` and a bounded one-second sample during a fixture. Windows WDDM/process-memory counter availability varies; missing counters are unknown, and shared system memory is not dedicated VRAM. NVIDIA/Microsoft direct documentation fetches failed; these are proposed operator diagnostics to verify on the machine, not observations of this user's GPU. No inference about 4/6/8 GB variants or model fit is warranted.

**Phase B: isolate cold loading and warm serving.** For one already-installed instruction model only, run one fixed cold request and two identical warm requests with output capped at 256 for the diagnostic task. Record residency before each request; intentionally unload only the chosen idle fixture model, never unrelated work. Use identical prompt/schema/context, single concurrency and no retries. Record client elapsed, first byte, first frame and first visible content separately; final total/load/prompt/eval durations, prompt/cache/output counts, finish reason, schema/semantic result, peak dedicated memory, CPU/GPU split and cancellation outcome. A tiny diagnostic output cap does not replace or reduce the real planner floor. Distinguish warm model residency from prompt/KV prefix caching.

**Phase C: paired complete planner fixtures.** Freeze three representative nonsecret fixtures (small server task, browser task with manual behavior checks, revision preserving earlier requirements). Compare baseline PLAN and a compact, schema-complete candidate on the same installed instruction model, same native runtime/schema, context 32,768, planner floor at least 8,192 and explicit wall/call allowance. One attempt per fixture/arm, deterministic validation unchanged; record all failures without automatic correction in this experiment. Initial ceiling: six invocations total. If a predeclared experiment wall budget is exceeded, stop and record censored/timeout results rather than claiming zero tokens or rerunning indefinitely. This small screening sample is not a statistically reliable benchmark. Promote only after a reviewed measurement cycle preserves full regressions/frozen replay values and demonstrates meaningful benefit without requirement loss.

**Phase D: reasoning control isolated from prompt edits.** Optional separate two-call fixture comparison only after exact model/runtime capability inspection: same reasoning model, same complete request, one supported thinking setting versus current default. Never change temperature, prompt layout and runtime simultaneously. If disabling thinking is unsupported, record unsupported rather than repeatedly retrying. A separate paired DeepSeek user-message-only/temperature experiment needs its own frozen fixture, contract preservation and explicit invocation allowance. Do not assume reasoning-free output is faster or better without observations.

**Phase E: transport behavior with fake local server first.** Verify cancellation during connection wait, model-load silence, reasoning-only frames, content generation and after the final frame; stalled reads; maximum bytes; malformed/truncated streams; missing terminal marker; length finish reason; and unchanged approved checks/source after failure. Distinguish time to request worker return, socket closure and observed server abort. A future timeout design should separate socket idle time from elapsed request budget, use bounded polling or a transport that can actually interrupt its worker, close in the owner, and join/terminate owned work before another request. Never claim hard cancellation from a foreground timeout that leaves a background inference worker running.

## Prioritized proposals for review

1. Replace contradictory examples with current schema-complete examples and add a static example/contract consistency check. Keep examples small but include all mandatory task/root fields and real behavior evidence. Preserve the original approved task as data, controller ownership, feature coverage and post-approval scope review.
2. Add timings/outcome diagnostics and precise user status (loading/prefill/reasoning/content only when observed; otherwise waiting). Preserve error class and full deterministic validation findings with bounded redaction. Surface timeout and schema rejection as different actionable results.
3. Introduce explicit runtime capability/version profiles for schema constraints, thinking controls, loaded context and timing extensions. Keep local endpoints loopback-only, redirects/proxies disabled, optional credentials redacted and explicit manual model choices intact. No automatic route change from calibration.
4. Measure compact complete planner prompts before reducing any included requirements or switching runtime. Preserve legacy/frozen context losslessly; disclose any newly reviewed omission/focus policy. Keep floor, hard context/output bounds, consent, global model-call/repair caps and frozen checks unchanged.
5. Consider new local deadline settings only with truthful semantics and cancellation tests. Merely increasing 120 to 300 seconds can hide loading/decode cost and occupy the worker longer; an exposed longer limit must remain explicit and bounded. Do not weaken guards or silently chain local/cloud attempts to make a wait seem successful.

No repository change is proposed as already implemented or tested. No source collection success is a live generation, benchmark, GPU-fit assessment or runtime setup completion.
