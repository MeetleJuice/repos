# Coding model evidence for Idea Foundry v0.26

Research/access date: **2026-10-20 UTC**. Read-only research; no repository edits, provider inference, paid requests, or model benchmarks were performed. This memo does **not** establish a current best model or a Foundry success rate. `source-register.json` records every attempted URL, access timestamp, status, and SHA-256 for retrieved bodies; `*.snapshot` retain the bodies.

## Decision

Do not change Foundry routing or advertise a model ranking from the supplied benchmark claims. The claimed **“FrontierCode GPT-6.1 Sol 60.4% (medium)” remains unauthenticated**: no authoritative matching result, task set, scaffold, sample count, reasoning configuration, cost, or evaluation artifact was retrieved. A blocked page is an access limitation, not evidence that the benchmark/model/claim is false. `frontiercode.ai` and `frontiercode.com` were discovery guesses, not authenticated publishers or citations supporting the claim. The model labels available to this agent are also not independent benchmark or public API availability evidence.

The AA Coding Index current composition, current leaders, and current model prices were **not verified** because the primary pages are blocked in this environment. SWE-bench Pro and LiveCodeBench primary repositories do provide useful methodological evidence, but their accessible sources cannot authenticate a complete 2026-10-20 ranking. Keep all proposed production model choices provisional pending a timestamped primary export and an authorized paired Foundry evaluation.

## Recommended Foundry evaluation protocol (proposal, not an executed experiment)

1. **Freeze the contract first.** Record baseline/candidate commit, model provider and exact discovered ID, endpoint/provider variant, model snapshot if available, effort, temperature, output ceiling, context policy, tool scaffold, prompts, retry/repair limits, timeout semantics, and code/test/fixture hashes. Preserve original approved tasks, checks and acceptance rules. Identify public benchmark version/time window and report author vs independent evaluations separately. No number from one benchmark substitutes for a Foundry result.
2. **Use three separate evidence sets.** (a) Public benchmarks inform candidate selection with their actual scaffold/effort/budget. (b) Existing labeled frozen Foundry replays check controller behavior and regressions; all eighteen handoff cases remain replay scenarios with mixed provenance, not eighteen independent model builds. (c) Newly authorized live tasks measure real Foundry builds; keep held-out tasks and include multi-file dependency edits, malformed/truncated responses, no-change responses, resumptions, interactive acceptance and repair after a real failing check. Do not use hidden checks as model input.
3. **Pair the live experiment.** Pre-register candidate list, task sample, replicates, seeds where supported, global invocation/repair ceilings and a cash ceiling before calling models. Run baseline/candidate on the same initial snapshots and task requirements, randomizing run order. Separate planner and builder changes; otherwise the result is a complete route comparison and cannot identify an individual model effect. Label pure local mode separately from cloud-assisted planning and count every route used.
4. **Measure checked outcomes.** Report first-attempt behavioral acceptance, completion within budget, regression retention, attempted calls, retries, repairs, retrieval calls, partial/cancelled output, wall time and failure category. Keep transport, quota/setup, output truncation, schema rejection, source-policy rejection, application failure, environmental cleanup, and manual acceptance distinct. Static source inspection / test pass / browser pass / user acceptance are distinct receipts. A builder self-report cannot pass verification.
5. **Report uncertainty honestly.** Publish numerator/denominator and paired per-task outcomes, including all failed/aborted attempts. Use paired bootstrap intervals or an appropriate paired comparison when sample size permits; a small local sample warrants a local observation only. Publish aggregate and per-task distributions; do not promote a winning model from a cherry-picked scenario or a mean that hides regressions. Set acceptance thresholds before results and require independent held-out confirmation before promotion.
6. **Separate the cost units.** A public score is not a token price, and token price is not cost per solved task or per session. Capture per-transport reported input/output/cached/reasoning tokens with the provider's category semantics and the dated price source. Count failed/retried/planner/retrieval/repair calls too. Mark missing usage and unavailable price categories `null`/unknown, never zero. Record measured billed USD when available separately from rate-card estimates; if reasoning tokens overlap output, avoid double billing in estimates. Keep local measured elapsed time/energy or declared infrastructure allocation separate from API dollars.
7. **Define task and session economics explicitly.** Per-attempt API estimate is sum of each billable token category times its documented rate / 1,000,000 plus any tool charges. Task total aggregates every invocation required by that approved task, including failed attempts. A session must have a declared start/end and include planning, all tasks, resumes and repairs; publish both total cost across all assigned tasks and cost per successful task, with failed-task spend retained. If any required component is unknown, total billed cost remains unknown or a clearly labeled partial subtotal; do not invent $/session. Pair cost with success/latency rather than optimize cheapest tokens alone.
8. **Retain review gates.** Replays never approve routing promotion, changed task scope, cloud consent or production scaffold edits. Proposed extra diagnosis/context/model calls need a measured benefit before production adoption. Capture every source, configuration, usage receipt and output hash for review, redacting credentials. No paid/live tests were authorized in this lane and none were run.

## Minimum evidence needed to resolve the supplied claim

Obtain the exact FrontierCode publisher/result URL (or archived primary export), timestamp, model identifier/provider, medium-effort meaning, benchmark/version/split and denominator, task-level outcomes, harness and tool policy, retry/turn/token/time budget, pass estimator, uncertainty and independent reproducibility artifacts. Obtain the AA methodology and dated leaderboard export rather than a screenshot alone. Provider pricing/usage receipts and authorized Foundry paired trials are additional requirements for cost/session or routing claims; benchmark scores alone cannot supply them.
